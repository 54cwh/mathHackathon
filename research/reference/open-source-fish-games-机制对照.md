## 一、结论先行

1. **最值得整体参考的是 `Test1609/big-fish-eat-small-fish`**（MIT，667 行单文件 Canvas）：面积守恒生长、体型分层生成、逃/追不对称检测半径、NPC 环绕边界，四项机制全部可直接对照到认领表 A2/A4/A5/A6。
2. **对你 BC 训练数据质量最有价值的是 `tghbrk/fish-eat-fish` 的三态状态机**（wander/hunt/flee + 状态计时器滞后），可用来给 ExpertPolicy 加 hysteresis，让专家轨迹更平滑。
3. **A4 生长系数问题被五个项目交叉确证**：你的 `biomass_to_size_gain=0.02` 比业界可玩口径低约 50–100 倍，「单局 size 几乎不动」是必然结果，不是 bug 是量纲选择。
4. **A8 escape 判定有更优备选**：游戏界通行做法是「限时追击 + 超时放弃」（Interactive 项目 180–300 帧追击上限），比现行的「目标切换即算逃脱」语义更干净。
5. **License 红线**：六个项目里只有 big-fish-eat-small-fish 和 Interactive_Fish_Eating_Game 是明确 MIT。所有项目都只建议「借鉴机制、自行重写、文献登记」，不要把代码或素材拷入仓库。

## 三、机制对照总表（以认领表 A2–A8 为行）

### A2 捕食几何（`capture_radius`、`κ`）

| 来源                                 | 距离判定                            | 体型阈值 κ                    | 备注          |
| ---------------------------------- | ------------------------------- | ------------------------- | ----------- |
| **你的 Arena** `config.py:49-50`     | 固定 `capture_radius=4.61`，纯距离无朝向 | 1.25                      | 半径不随体型缩放    |
| ① big-fish `index.html:392-418`    | `d < r1 + r2`（半径和）              | 玩家吃 NPC 1.12；NPC 互吃 1.20  | 捕食圈随体型自然放大  |
| ③ fish-eat-fish `enemy.js:228,241` | 半径和                             | 可食 0.8× / 危险 1.2×（对称 20%） | 与你 1.25 最接近 |
| ④ Interactive `fish.py:145,331`    | `d < (size1+size2)/2`           | **1.5**                   | 谱系最严        |
| ③ ai-player `ai-player.js:148,367` | —                               | **1.05**                  | 谱系最宽        |

**要点**：业界 κ 全谱系 1.05–1.5，集中在 1.12–1.25，你的 1.25 在谱系内偏严但合理。真正的差异在**距离口径**：游戏普遍用「半径和」让捕食圈随体型缩放，你的固定 4.61 意味着鱼长到 2.5 倍后相对捕食圈反而变小——这在「大吃小」叙事里是反直觉的，A2 认领时值得权衡。

### A3 能量四系数

| 来源                                 | 模型                                          | 数值                              |
| ---------------------------------- | ------------------------------------------- | ------------------------------- |
| **你的 Arena** `config.py:38-42`     | 持续耗（base 0.0008 + move 0.0015·v²）+ 吃食回 0.12 | 600 步基础总耗 ≈ 0.48；每吃 1 条回 12% 上限 |
| ⑤ Fish-Eat `FishPlayer.py:111-115` | 耐力制：按键移动每帧 −2，静止每帧 +0.5                     | 「动才耗、静则回」                       |

**要点**：你的模型是「持续代谢压力」，比游戏口径苛刻——全速游动时每步耗 0.0023，约 435 步耗尽，**一条不吃必死，每局至少吃 ~4 条才能活到 600 步**。这是合理的生态压力设计，但 play-test 验证存活率时要带着这个先验：若实测存活率过低，优先调 `food_reward` 而非 `base_cost`。

### A4 生长（问题最严重的项）

| 来源                                     | 生长公式                                              | 单局量级                                    |
| -------------------------------------- | ------------------------------------------------- | --------------------------------------- |
| **你的 Arena** `env.py:207-210`          | `size += 0.02 × prey.size`（prey≈0.45 → 每次 +0.009） | 理论上限 ~1.09，实测 1.01，`max_size=2.5` 永远摸不到 |
| ① big-fish `index.html:371-375`        | **面积守恒带损耗**：`r = √(r² + r_prey² × 0.35)`          | 边际递减内生，无需调参                             |
| ⑤ Fish-Eat `FishPlayer.py:142`         | `growth = prey.size × (0.2 − 0.01×size/10)`       | 自身越大长得越少（显式边际递减）                        |
| ④ Interactive `fish.py:333`            | `growth = min(prey.size/12, self.size)`           | 随猎物线性、随自身封顶                             |
| ③ fish-eat-fish `ai-player.js:314-327` | 离散等级制：每级 `+5+⌊i/2⌋×2`                             | 等级越高每级越大（反边际递减，为关卡服务）                   |

**要点**：四个连续生长项目全部让「吃一条」产生**自身体型 1%–10% 量级**的变化；你的 0.02 系数产生的是 0.9%。若想一局内「大吃小」可见，`biomass_to_size_gain` 需提到 0.5–2.0 区间，或直接换成 ① 的面积模型（`size = √(size² + prey²×g)`，g≈0.1–0.35），后者还有一个好处：`max_size` 可以弱化甚至去掉，边际递减天然防爆。

### A5 actors（速度、检测/释放半径）

| 来源                                      | 猎物速    | 天敌巡航/追击     | 检测 / 释放           | 逃逸检测            |
| --------------------------------------- | ------ | ----------- | ----------------- | --------------- |
| **你的 Arena** `config.py:56-70`          | 0.35   | 0.40 / 0.65 | 15 / 22（滞后带）      | prey 无主动逃逸（MVP） |
| ① big-fish `index.html:322-338`         | —      | 逃速=追速=体型速度  | 逃 d<180 / 追 d<300 | 小 0.88× 即逃      |
| ④ Interactive `fish.py:144-159,231-251` | 1–3 随机 | 追击时 ×1.5 加速 | 逃 d<250 / 追 d<200 | >1.5× 即逃        |

**要点**：

- 「逃跑检测半径 < 追击检测半径」（① 的 180/300、④ 的 250/200 相反）两种方向都存在；你的 detect 15 / release 22 滞后带设计与 ① 同向（给猎物留逃生窗口），思路正确。
- 注意一个你特有的平衡点：鱼的归一化速度上限 v=1.0 > 天敌追击 0.65（`env.py:176`），鱼绝对速度比天敌快，游戏界通常反过来（天敌更快但转弯慢）。你的 `predator_turn_rate=5.0 rad/s` 是否已经构成足够威胁，需要 play-test——若鱼随便就能甩开天敌，predation pressure 会失效，`escape_successes` 指标也会失真。

### A6 边界策略

| 来源                                    | 策略                     |
| ------------------------------------- | ---------------------- |
| **你的 Arena** `entities.py:24-25`      | clamp（贴墙卡住、持续耗能）       |
| ① big-fish `index.html:293,355-358`   | 玩家 clamp；**NPC 环绕回卷**  |
| ③ fish-eat-fish `enemy.js:181-201`    | **反弹**（触边后角度重采样朝场内）    |
| ④ Interactive `fish.py:82-83,323-326` | 玩家 clamp；NPC 出界即移除+补生成 |

**要点**：clamp 对可复现性最友好（无 Teleport、无随机重采样），「贴墙耗能」甚至可以解读为生态成本；但如果 Demo 演示时鱼群集体卡墙角会很难看。折中：鱼保留 clamp，prey/predator 改反弹或回卷（它们是脚本实体，不受影响网络训练的公平性）。

### A7 碰撞语义

你的现状（`env.py:183-191`：只计数、无位移、无能量后果）在游戏界没有反例——⑥ DragonFeast 的障碍物是伤害性的（碰到掉血/即死），但那属于关卡设计不是生态仿真。维持「仅计数」可行；若未来想让障碍成为选择压的一部分，⑥ 提供了「障碍 = 负奖励事件」的接法（撞障碍已有 `arena.collision` 事件，fitness 侧扣分即可，不需要动 Arena）。

### A8 escape 判定

| 来源                                  | 机制                                                         |
| ----------------------------------- | ---------------------------------------------------------- |
| **你的 Arena** `env.py:275-284`       | 天敌切换目标 → 被弃目标记「逃脱成功」                                       |
| ④ Interactive `fish.py:124,205-208` | **限时追击**：`max_chase_time` 180–300 帧（3–5 s @60fps），超时主动放弃目标 |

**要点**：「限时追击 + 超时放弃」是更干净的语义：逃脱的因果链是「猎物拉开距离/撑过追击窗口 → 天敌放弃」，而现行「切换目标」会把「天敌只是看到更近的鱼」误记为逃脱。若采纳，escape 的定义变为「被追击后存活至 release_radius 之外或追击超时」，与 `policies.py` 已有的 release_radius 滞后带天然兼容。

## 四、对 ExpertPolicy 与前端 Demo 的专项发现

### ExpertPolicy（`arena/policies.py:19-31`）

你现行是线性加权转向（猎物吸引 − 威胁 − 障碍，饥饿增益）。③ fish-eat-fish 的 `ai-player.js:121-232` 提供了一个更适合做 BC 教师信号的结构：

1. **三态状态机**：wandering / hunting / fleeing，fleeing 强制优先（威胁 <200 时无条件切入，锁 60 帧）；
2. **状态计时器滞后**：每个状态有 `stateTimer`（60–300 帧），防止逐帧抖动切换；
3. **追击方向加随机扰动** ±π/8 ~ ±π/4，避免专家轨迹是「完美直线」导致 BC 学到过脆的策略。

这三点直接决定专家轨迹的平滑度与可学习性，属于「BC 训练 → ΔW」分支的上游质量问题，按流水线规则应在 policies 层解决。

### 前端 Demo（WS 帧快照 → Canvas 渲染）

- ① 的 `drawFish`（`index.html:485-560`）是**纯 Canvas 矢量鱼**：椭圆身 + 二次曲线鳍 + `sin(phase)` 摆尾，摆尾频率随速度加快（`phase += dt×(6+0.12×speed)`，:304）。零素材依赖，可直接改写为 React 组件内的渲染函数，鱼体长宽比按 `size` 缩放即可。
- ③ 的**三色可食性描边**（绿 = 可食 / 红 = 危险 / 黄 = 相近）用于 Demo 讲解时极其直观：观众一眼看出「这条演化后的鱼在追绿的、躲红的」。建议在 Demo 渲染层加按 `size_ratio` 与 κ 着色的描边，配合 κ=1.25 的冻结值。
- ② 的 `Spawner.js:29-64` **按玩家等级动态调权**（同级 ×2.0、高一级 ×1.5、低一级 0.3^diff 指数衰减）若未来要做「难度自适应的 live demo」可借鉴；对实验本体无用（实验要求固定 seed 固定布局）。
